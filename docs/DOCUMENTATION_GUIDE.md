# 文档编写规范

本规范适用于仓库内 Markdown 文档，目的是让不同贡献者基于同一份当前事实维护项目说明。

## 文档职责

- `README.md`：项目简介、当前功能概览、构建入口和主要文档链接。保持简短，不复制专题细节。
- `docs/PROJECT_OUTLINE.md`：当前架构、功能状态和模块职责。
- `docs/<功能>.md`：单一功能的行为、资源约束、硬件依赖、错误处理和验证方法。
- `tools/<工具>/README.md`：工具用途、运行命令、输入输出和验证边界。
- `CHANGELOG.md`：已经发布且消费者可感知的最终变化。
- 预览和测试说明：只描述其模拟或验证的范围，不将模拟结果写成设备实测。

避免同一事实在多个文件中维护详细副本。确需引用时链接到权威文档；README 和项目大纲只保留摘要。

## 状态与证据

使用以下明确状态：

- **已实现**：代码中存在完整的用户操作路径。
- **部分实现**：核心路径存在，但有明确缺失或限制；应说明缺少什么。
- **占位**：只有入口、演示或通用提示，没有完整业务路径。
- **规划中**：尚未实现的目标。
- **已移除**：代码中不再提供，必要时说明替代方式。

验证结论分开写：

- **主机测试**：写明测试命令和覆盖范围。
- **编译验证**：写明 PlatformIO 环境、结果及 RAM/Flash 数值。
- **实机验证**：写明设备侧实际观察到的行为。

一个层面的通过不代表其他层面通过。历史验证应附日期并标注为历史结果，不应放在“当前结果”段落里。

## 表述和格式

- 使用简体中文、具体短句和统一术语；必要的英文 API、路径、命令使用反引号。
- 标题使用 `#` 到 `###` 的层级，不跳级；一个文档只设一个一级标题。
- 日期统一使用 `YYYY-MM-DD`；版本写成 `0.2.1`，Build 写成 `12`。
- 路径、按键、日志前缀、文件名和资源数值应与代码或工具一致。
- 区分“设计目标”“当前实现”“验证结果”和“历史记录”，不要混在同一列表。
- 写限制时说明触发条件和用户可见结果，不使用含糊的“可能有问题”。
- 相对链接以当前 Markdown 文件所在目录为基准。修改文档后检查目标文件存在且链接未失效。
- 删除或改名文档前，先更新所有入站链接。

## CHANGELOG 规则

`CHANGELOG.md` 面向普通消费者：记录已经生效的新增、改进和修复，优先描述最终体验。每条使用用户能理解的语言；不记录实现过程、源码路径、测试过程、资源数字或未完成计划。版本日期倒序排列，不确定或尚未发布的内容不写入已发布日志。

## 更新流程

1. 先从代码和当前测试确认行为，不用旧文档推断当前实现。
2. 修改功能后更新该功能的权威专题文档；若用户可见状态改变，再更新 README、项目大纲或 CHANGELOG 对应部分。
3. 搜索旧术语、旧版本号和重复状态，更新关联链接。
4. 检查 Markdown 路径、相对链接、标题层级和表格格式。
5. 纯文档改动无需固件编译；涉及代码、资源、构建配置或固件行为时按仓库要求执行完整构建并报告资源占用。
