# SD 卡点阵字库

## 当前状态与使用

固件已能按需读取 `tools/font_builder` 生成的 NBFT v1 单色字库，支持 32 位 Unicode 码点、四字节 UTF-8、基线偏移和透明绘制。入口为 **设置 → 设备自检 → SD字库测试**。其他页面保留内置字体；当前阶段用于验证 SD 读取和显示，尚未减少内置字库或固件体积。

将导出的三个文件放入 SD 卡：

```text
SD 卡根目录/
  Font/
    font-14.bin
    font-20.bin
    font-24.bin
```

`Font` 是当前约定目录。文件名与文件头中的字号必须一致，不能通过改名转换字号。`manifest.json` 可留作电脑端核对，但固件不解析它，也不依赖它查找字库。

进入页面默认打开 14 px；`Up/Down` 循环选择 14、20、24 px，`OK` 重新挂载并重试当前字号，普通或长按 `Left` 关闭文件、卸载 SD 并返回自检列表。检查期间同样可以切换或返回。标题、操作和错误提示使用内置字体，因此字库不可用时仍可操作。

样张包含中文、标点、英文、数字、重音字符，以及扩展区字符“𠮷”（U+20BB7）。能否显示某个字符取决于源字体是否提供该字形；缺字显示占位框。当前不做字距配对、复杂文字塑形、双向排版、变体序列或彩色 Emoji。

## 模块与调用顺序

| 模块 | 职责 |
| --- | --- |
| `bsp/SdFontFile` | 只读文件、定点读取与边界检查，不负责挂载 |
| `services/SdBitmapFont` | 文件头、CRC、Unicode 索引查询、度量与缓存，不绘图 |
| `ui/SdBitmapText` | UTF-8 解码、测宽、基线绘制、裁剪和缺字框 |
| `ui/pages/SdFontTestPage` | 三个字号的选择、重试、样张与错误展示 |
| `DeviceSelfTestPage` / `UiManager` | 返回路由、挂载会话、分步推进和 SD 所有权切换 |

使用顺序：

1. 关闭旧字库句柄，确保 GPIO16 为 LOW，再通过现有 `SdCardService` 挂载 SD。
2. `font.open(14)` 检查文件头和长度，成功后进入 `Checking`；返回成功不表示 CRC 已通过。
3. 主循环调用 `font.tick()`，仅 `Ready` 时可以查字或绘制；`consumeChanged()` 用于触发状态变化后的重绘。
4. `SdBitmapText::measureUTF8()` 按字形进位测宽；`drawUTF8()` 接收左侧笔位置、基线及裁剪矩形，写入现有帧缓冲。背景由调用页面先清理。
5. 退出或更换 SD 所有者前先 `font.end()`，再卸载 SD；不可先卸载后继续使用旧字形对象。

`Glyph` 带有会话编号，重新打开后旧会话字形不能用于读取。页面退出、进入「SD卡转USB」和休眠卸载 SD 前均关闭读取器。当前只在用户进入字库测试时打开文件，不启动后台扫描；CRC 检查时临时使用现有自检 CPU 提速，完成后释放该请求。

## 资源与格式边界

- 文件头 64 bytes，索引记录 24 bytes；全部按小端字段解析。详细定义见 [NBFT v1](../tools/font_builder/FORMAT.md)。
- 每次打开、切换字号或重试都校验完整 payload CRC32。每次 `tick()` 最多读取 8 KiB，使用 1024-byte 栈缓冲，在步进之间继续处理按键。实际单次读卡耗时仍受 SD 驱动和卡片影响。
- 以 uint32 索引二分查字，不整体加载文件或字符索引。索引缓存为 16 条记录（384 bytes），字形缓存为 8 槽，每槽 128 bytes 点阵，也缓存缺字结果。
- 超过缓存容量的字形按行读取；单字宽、高上限均为 1024，绘制栈缓冲为 128 bytes。小字体不要求固定的 `字号×字号` 点阵。
- 检查文件头、长度、CRC、所访问记录的码点/标志/范围、点阵长度及行末补位。设备不再遍历验证全部索引排序与连续性，依赖导出工具完成结构验证；CRC 也不是签名认证。
- 无卡、缺文件、字号不符、损坏或读取失败均有提示，可按 OK 重试。错误会关闭文件并清理缓存。拔卡后已缓存字形可能仍能绘制，直到下一次实际文件访问才报告读取失败，不宣称即时检测热拔卡。
- 帧缓冲绘制遵守当前屏幕旋转和页面裁剪。`measureUTF8()` 使用进位而非墨迹包围框；换行使用文件记录的行高。

本次实际导出使用 `SourceHanSansOLD-Normal-2.otf`、阈值 115，每份包含 44,650 字符，其中 2,495 个位于 U+FFFF 以上：

| 字号 | 文件大小 | 上升部 / 下降部 / 行间隔 | 行高 | 最大单字点阵 |
| --- | --- | --- | --- | --- |
| 14 px | 2,247,630 bytes | 18 / 8 / 1 | 27 px | 52 bytes |
| 20 px | 3,291,708 bytes | 27 / 11 / 2 | 40 px | 76 bytes |
| 24 px | 3,951,908 bytes | 32 / 14 / 3 | 49 px | 92 bytes |

这些数据只对应当前源字体和导出参数。未来替换全局字体前，需重新检查各页面的基线、测宽、行高和缺字策略；不能直接用字号代替行高。

## 硬件与日志

沿用现有 **SD_MMC 1-bit**：CLK=GPIO11、CMD=GPIO12、D0=GPIO10。`BoardConfig` 中 MISO/MOSI 是旧别名，此处没有改成 SPI。GPIO16 LOW 时由设备读卡，HIGH 时转给板载 USB-to-SD 芯片；不能在电脑持卡期间同时访问 SD。

字库日志前缀为 `[FONT]`，记录打开路径、通过后的字号/字符数/长度以及失败阶段；添加编译宏 `OB_SD_FONT_LOG_ENABLED=0` 可关闭。挂载日志继续由现有 SD 服务提供。实际 SD 挂载、路由切换和退出后的恢复需在目标 PCB 验证。

## 验证与验收

主机验证命令和覆盖范围见 [SD 字库验证工具](../tools/sd_font_tests/README.md)。它运行生产读取、绘制和页面代码，使用实际三份 BIN，并与 Python 独立解码结果比较。2026-10-21：读取/异常/缓存用例通过，18 组逐像素比较通过，合览为 `tmp/sd-font-test/sd-font-framebuffers.png`。

完整 `pio run -e esp32s3` 通过：RAM **97,392 bytes（29.7%）**，Flash **3,957,275 bytes（53.9%）**；较提交 `39e5192` 增加 1,736 bytes RAM、5,748 bytes Flash。构建记录 `tmp/sd-font-build-20261021.log`。本次未烧录，主机文件系统替身不能证明实际读卡速度或物理显示效果。

实机验收顺序：

1. 使用主项目固件启动，进入测试页，确认三个字号的中文、数字、重音和“𠮷”显示完整。
2. 检查期间按 Left 取消，重新进入并双向切换字号，验证重试、焦点和返回。
3. 分别测试无卡、缺文件和重新复制后的重试，记录实际校验等待及按键响应。
4. 退出后进入阅读/音乐确认 SD 可重新挂载；再测试 SD卡转USB 的进入、电脑安全弹出、退出及再次读取字库。

全局字体迁移、减少内置字库与 OTA 包体积是后续阶段，以这些实机结果和逐页布局检查为前提。
